\section{Pipeline Design}
\label{sec:ch6.section1}
%----------------------------------------------------

Based on the nature of the data collected (see Chapter \ref{ch:data_collection}), the \ac{LiDAR} processing tools available in MATLAB, and the objectives of this investigation, the following processing steps were selected to be evaluated as part of the proposed data processing pipeline:
\begin{itemize}
    \item Motion Compensation
    \item De-noising
    \item Wave Parameter Estimation
    \item Pancake Identification
\end{itemize}

%----------------------------------------------------
\subsection{Motion Compensation}
\label{subsec:ch6.section1.subsec1}

Observing a moving target scene (sea ice in the \ac{MIZ}) from a moving platform (\textit{S.A. Agulhas II}) introduces motion distortion into the captured point cloud data and increases the level of complexity required in the data processing pipeline. The motion of the observation platform causes the sensor to change position and orientation between capturing frames, reducing the accuracy of concatenated frames and making it more difficult to identify and track features in the scene, such as individual ice floes and wave parameters.

A solution to this complication is to apply motion compensation to the point cloud data before further processing. A Kalman filter can be used to estimate the roll and pitch angles (yaw estimations will not be accurate enough to be of use) of the observation platform during data collection. With these angle estimates, it may be possible to apply an inverse transform to the point cloud data to compensate for some motion induced by the observation platform. If successful, this motion compensation will simplify the point cloud processing required and improve the quality of the final outputs.

%----------------------------------------------------
\begin{figure}[H]
    \centering
    \includegraphics[width=0.82\textwidth]{figs/ch6/scene_frames.png}
    \caption{\textbf{Reference Frames and Coordinate Systems.}}{The World and vessel frames are based on the NED convention, while the Avia and point cloud frames are based on the sensor's local coordinate system as defined by the manufacturer. Sea ice observed in the target scenes does not have a native coordinate system, so for the purposes of this investigation, the sea ice coordinate system is defined as being the same orientation as the Avia's local coordinate system.}
    \label{fig:scene_frames}
\end{figure}
%----------------------------------------------------

To compensate for the motion of the observation platform, it is necessary to understand the different reference frames and coordinate systems involved in the data collection process, see Figure \ref{fig:scene_frames}. The Avia has its own local coordinate system, as defined by the sensor's orientation and position on the vessel. As seen in Figure \ref{fig:avia_axes}, the Avia's local coordinate system is defined with the x-axis pointing forward, out of the sensor aperture, the y-axis pointing to the left of the sensor and the z-axis pointing upwards. The point cloud data captured by the Avia is represented in this local coordinate system, with the origin at the sensor aperture. The coordinate system of the \textit{S.A. Agulhas II} is based on the \ac{NED} convention, with the x-axis pointing North (the bow of the vessel), the y-axis pointing East (to the starboard) and the z-axis pointing downwards. The origin of the vessel's coordinate system is located at the centre of mass of the vessel. The sea ice under observation has no native coordinate system, and for the purposes of this investigation, the sea ice coordinate system is defined as being the same orientation as the Avia's local coordinate system, but with its origin at the centre of the target scene (the point cloud frame). All these coordinate systems are located within the World frame, which is a fixed reference frame used for navigation and mapping. The World frame is typically defined using a geodetic coordinate system, such as WGS84, with the origin at the Earth's centre of mass (\cite{perezKinematicModelsManoeuvring2007}). The World frame also makes use of the \ac{NED} convention in this investigation.

With the data available from the Avia, it is only possible to estimate changes in roll and pitch attitude, and not translation or yaw of the sensor. As such, the motion compensation will not be able to fully map the Avia's local coordinate system to the vessel frame or the World frame through a rigid body transformation. Instead, the motion compensation will apply an inverse transform to the Avia's local coordinate system in an attempt to align the Avia's x- and y-axes to be horizontal with the World frame's x- and y-axes, to 'level' the point cloud data.

\subsection{De-noising}
\label{subsec:ch6.section1.subsec2}

When the Avia collects data in adverse environmental conditions (such as rain, snow, and fog), the beam emitted by the sensor may interact with these weather conditions, leading to poor quality and/or noisy data. Points created by interactions with adverse weather conditions almost always have a very low return intensity (less than 4 out of 255) as the targets they interact with (snow or rain) are incredibly small and far less reflective than the intended target scene. In the case of data collected from the \ac{SCALE} Winter 2022 Cruise, snowy conditions resulted in unwanted returns caused by snowflakes in the area immediately in front of the sensor's minimum detection range. These unwanted returns create difficulties when trying to process the data further as well as reducing the number of usable points per frame.

\subsection{Wave Parameter Estimation}
\label{subsec:ch6.section1.subsec3}

\ac{RANSAC} has been applied with great success in identifying and reconstructing buildings in urban environments from airborne \ac{LiDAR} data (\cite{forlaniBuildingReconstructionVisualization2003}), but has seen limited use in natural environments. Because \ac{RANSAC} fits a user-defined model to data, a sufficiently complex wave model could allow for the identification of features in the \ac{MIZ}, such as surface waves propagating through an ice field. This would require a suitable wave model to be developed, but if successful could allow for the extraction of wave parameters such as amplitude and wave period directly from point cloud data.

The estimated wave parameters could be used to improve understanding of wave-ice interactions in the \ac{MIZ}, as well as providing in-situ data for the improvement of current models of wave propagation, attenuation and interactions with sea ice. These data could also be used in the validation of estimates from other remote sensing methods used to observe the \ac{MIZ}, such as \ac{SAR}.

For the Aalto University data, a simple linear sinusoidal wave model should be sufficient, as the wave makers generated relatively uniform waves and constrained their complexity. In contrast, data from the \ac{SCALE} Cruise will require a more complex model to account for the increased dynamics and irregular wave behaviour in the \ac{MIZ}, which is driven by multiple environmental factors and interaction with the vessel itself.

Due to the complexity of wave behaviour in the \ac{MIZ}, and modelling challenges associated with it, as well as the lack of ground truth data, this investigation will focus primarily on the Aalto University data for wave parameter estimation.

%----------------------------------------------------
\begin{figure}[H]
    \centering
    \includegraphics[width=0.82\textwidth]{figs/ch6/WaterWave_Stokes1st2nd.png}
    \caption{\textbf{First Order (Linear) and Second Order Stokes Waves.}}{First order waves are a simple sinusoidal function of wave height over time, while second order Stokes waves include greater complexity. Stokes
        Taken from \textcite{benitzSimulatingHydrodynamicsOffshore}}
    \label{fig:stokes}
\end{figure}
%----------------------------------------------------

As seen in Figure \ref{fig:stokes} above, a first order (linear) wave model is a simple sinusoidal function of wave height over time, and is the most basic wave model. A second order Stokes wave model includes additional terms to account for non-linear effects and better represent the behaviour of gravity waves. These second order waves display a characteristic asymmetry between the wave crest and trough, with the crest being sharper and higher than their first order counterparts, and the trough being broader and shallower. \textcite{benitzOceanHydrodynamicsEngineers} gives the Equations for first and second order Stokes waves as shown in Equations \ref{eqn:first_ord} and \ref{eqn:second_ord} respectively. It can be clearly seen that the second order Stokes wave model includes many more terms than the first order model, which allows it to better represent the behaviour of real waves, but also makes it for more complex to fit to data. 

%----------------------------------------------------
\begin{equation} \label{eqn:first_ord}
    \eta = Asin(kx - \omega t +\theta)
\end{equation}
%----------------------------------------------------

%----------------------------------------------------
\begin{equation} \label{eqn:second_ord}
    \eta = Asin(kx - \omega t +\theta) + \frac{H^2}{2L}\frac{cosh(kh)(2+cosh(2kh))}{sinh^3(kh)}cos(kx - \omega t +\theta)
\end{equation}

\subsection{Pancake Identification}
\label{subsec:ch6.section1.subsec4}

To identify the size and shape of individual pancakes, a method to associate individual points with individual pancakes is required. This can be achieved using a suitable clustering algorithm. The choice of clustering algorithm will be determined by the characteristics of the data to be clustered and the desired output.

The input data for the clustering algorithm will be the point cloud data's three-dimensional coordinates (x, y, z). The return intensity of each point was not considered as an input feature for clustering, not enough is known about how the return intensity varies across individual pancakes, and it is hypothesised that the return intensity values obtained are influenced by environmental factors such as angle of incidence rather than physical characteristics of the pancakes themselves. The desired output of the clustering algorithm is a set of clusters, where each cluster represents an individual pancake. Each point in the point cloud data should be assigned to a cluster, with points that do not belong to any pancake being classified as noise or outliers.

Frames to be clustered were selected by visual inspection of the raw point cloud data and video footage from the camera mounted several decks above the Avia (\cite{passerottiSCALEWIN22SAAgulhas,passerottiSCALEWIN22SAAgulhasa,passerottiSCALEWIN22SAAgulhasb}), to identify frames with clear pancake formations, high point densities and minimal motion artefacts. Scenes with consolidated ice floes were avoided as the clustering algorithms are designed to identify discrete clusters of points, and scenes with consolidated ice floes do not contain clear boundaries between individual pancake floes. Once a frame was selected, the clustering algorithms were applied to it as well as a frame composed of a concatenation of the initial frame and the following frame. This was done to investigate if increasing point density improved clustering performance. No more than two frames were concatenated as the target scenes were dynamic, and concatenating more frames risked introducing motion artefacts, which could lead to erroneous clustering results.

After inspecting both the point cloud and video data, four scenes from three datasets were selected for clustering analysis, see Table \ref{tab:clust_scene} and Figures \ref{fig:scenes} and \ref{fig:map}.

Three density-based clustering algorithms were considered for this application: \ac{DBScan}, \ac{VDBScan}, and \ac{OPTICS}.

\ac{DBScan} is one of the oldest and most widely used density-based clustering algorithms. It makes use of two key parameters set by the user: \textbf{$\epsilon$} (the radius of the neighbourhood around a point) and \textbf{MinPts} (the minimum number of points required to form a dense region). Using the \textbf{$\epsilon$} and \textbf{MinPts} parameters, \ac{DBScan} classifies points into three categories: core points (points with at least \textbf{MinPts} points within their \textbf{$\epsilon$} neighbourhood), border points (points that are not core points but are within the \textbf{$\epsilon$} neighbourhood of a core point), and noise points (points that are neither core nor border points) (\cite{esterDensityBasedAlgorithmDiscovering1996}). The algorithm is relatively efficient and easy to implement. However, \ac{DBScan} relies on the assumption of constant density within clusters, which may not hold true for the variable density of points in the point cloud data collected by the Avia.

\ac{VDBScan} is an extension of \ac{DBScan} that addresses the issue of variable density within clusters. Like \ac{DBScan}, it uses the \textbf{MinPts} parameter, but instead of a fixed \textbf{$\epsilon$} value, makes use of a parameter \textbf{k} (the number of nearest neighbours to consider) to calculate a variable \textbf{$\epsilon$} value for each point based on the local density of points (\cite{liuVDBSCANVariedDensity2007}). This allows \ac{VDBScan} to adapt to changes in point density, making it more suitable for the Avia point cloud data. However, \ac{VDBScan} is more complex and computationally intensive to implement than \ac{DBScan}.

\ac{OPTICS} is another algorithm related to \ac{DBScan}, that similarly to \ac{VDBScan}, addresses the issue of variable density within clusters. Instead of producing a set of clusters directly, \ac{OPTICS} uses a single \textbf{MinPts} parameter to produce core distances and reachability plots. This information can be used to extract clusters of varying densities, using \textbf{k}, a user-defined reachability distance threshold (\cite{ankerstOPTICSOrderingPoints1999}). \ac{OPTICS} is more flexible than both \ac{DBScan} and \ac{VDBScan}, as it computes a complete ordering of the data points before extracting clusters. However, it is the most computationally intensive of the three algorithms.

\section{Data Extraction}
\label{sec:ch6.section2}
%----------------------------------------------------

The starting point for the pipeline is the raw Avia point cloud data. All data used in this investigation was captured as rosbag (\emph{.bag}) or the proprietary Livox file type (\emph{.lvx}). The raw data has to first be extracted from these file types before it can be processed or used in analysis. The Livox \ac{ROS} driver includes functionality to convert \emph{.lvx} files to \emph{.bag} files. MATLAB's \ac{ROS} Toolbox contains functions and tools for extracting data fields from a \emph{.bag} file for storage and use in standard MATLAB matrices or structures.

\ac{IMU} data (linear \& rotational accelerations and timestamps) captured by the Avia is extracted from the \emph{.bag} files and then stored in matrices for further processing.

MATLAB's \ac{LiDAR} Toolbox has provision for a \emph{pointCloud} object which was used to store all \ac{LiDAR} data for processing and analysis. This object contains fields for the point cloud's x, y and z coordinate data, total number of points, as well as point colours, normals and intensities. The Avia is only capable of directly measuring point intensity, so this was the only additional data field extracted from the .bag files into the \emph{pointCloud} object. Frame timestamps are not stored in the pointCloud object, but in a standalone array.

\section{Proposed Pipeline}
\label{sec:ch6.section3}

%----------------------------------------------------
\subsection{Motion Compensation}
\label{sec:ch6.section3.subsec1}

Two Kalman filters were implemented to estimate the attitude of the Avia during data collection. The filters output estimates of the sensor's roll and pitch (yaw cannot be reliably estimated from \ac{IMU} data). Using these angle estimates an inverse transform can be applied to the point cloud to 'stabilise' the data and compensate for the motion of the observation platform. As these Kalman filters only estimate changes in roll and pitch attitude, and not position, there will still be motion artefacts in the data due to translation and yaw of the observation platform. 

%----------------------------------------------------
\begin{figure}[H]
    \centering
    \includegraphics[width=0.82\textwidth]{figs/ch6/motion_comp.png}
    \caption{\textbf{Motion Compensation Pipeline.}}
    \label{fig:motion_compensation}
\end{figure}
%----------------------------------------------------

The first Kalman filter was implemented using MATLAB's Sensor Fusion Toolbox. This filter implements an \ac{ESKF}, a variation of the traditional Kalman filter designed specifically for attitude estimation from \ac{IMU} data. This filter, instead of estimating the full state of the system, estimates only the error in the state, which allows for better handling of non-linearities and noise in the measurements (\cite{vitaliRobustErrorStateKalman2021}). The second Kalman filter implemented was a traditional \ac{KF}, which was initially developed by Philip Salmony (\cite{salmonyPms67AttitudeEstimation2025}). Both filters accept the Avia \ac{IMU} data as inputs (two M x 3 matrices, one containing linear accelerations (\textit{A}) and the other gyroscope measurements \textit{W}) and return an M x 3 matrix (\textit{S}) containing roll (Avia's x-axis) and pitch (Avia's y-axis) estimates at the same frequency as the input data (200 Hz). The final column of the output matrix is not used as yaw cannot be reliably estimated from \ac{IMU} data, and is set to zero, as shown in Equation \ref{eqn:orient}. As the transform will only be about two axes (roll and pitch), the signs of the angles were inverted to allow for the final rotation matrix (\textit{$R_W^A$}) to be directly applied, without the need for the creation of an inverse rotation matrix.

%----------------------------------------------------
\begin{equation} \label{eqn:orient}
     S = 
     \begin{bmatrix}
    \phi_{0} & \theta_{0} & 0 \\
    \phi_{1} & \theta_{1} & 0 \\
    \cdot & \cdot  & \cdot  \\
    \phi_{m}& \theta_{m} & 0 \\
    \end{bmatrix}
\end{equation}
%----------------------------------------------------

Once angle estimations have been obtained, they have to be time synchronised and matched to their corresponding point cloud frames. Each angle estimation and frame has an associated timestamp that was used to match frames with angle estimations. Angle estimations are produced at 200 Hz while point cloud frames are produced 20 times slower, at 10 Hz. The list of frame timestamps was iterated through, and matched with its associated angle estimation timestamp. If no exact match was found, then the angle estimation closest in time was associated to the frame. This produced an index list of angle estimations from matrix \textit{S} that corresponded to each frame in the point cloud data.

Next, a rotation matrix (\textit{$R_W^A$}, see Equation \ref{eqn:rot}) to translate the point cloud data from the Avia frame to the World frame, was created for each point cloud frame from its associated angle estimation, using the MATLAB \textit{rigidtform3d} function. The \textit{rigidtform3d} function accepts a row vector of three angles (roll, pitch and yaw) from matrix \textit{S} and returns a 3 x 3 rotation matrix, \textit{$R_W^A$}. The rotation matrix can be created through the multiplication of two individual rotation matrices, one for roll (\textit{$R_x$}, Equation \ref{eqn:rotx}) and one for pitch (\textit{$R_x$}, Equation \ref{eqn:roty}). A yaw rotation matrix does not need to be included as the yaw angle is set to zero and this will result in an identity matrix. 

%----------------------------------------------------
\begin{equation} \label{eqn:rotx}
     R_x(\phi) =
    \begin{bmatrix}
    1 & 0 & 0 \\
    0 & \cos\phi & -\sin\phi \\
    0 & \sin\phi & \cos\phi
    \end{bmatrix}
\end{equation}
%----------------------------------------------------

%----------------------------------------------------
\begin{equation} \label{eqn:roty}
    R_y(\theta) =
    \begin{bmatrix}
    \cos\theta & 0 & \sin\theta \\
    0 & 1 & 0 \\
    -\sin\theta & 0 & \cos\theta
    \end{bmatrix}
\end{equation}
%----------------------------------------------------

%----------------------------------------------------
\begin{equation} \label{eqn:rot}
    R_W^A \;=\; R_y(\theta)\,R_x(\phi)
    \;=\;
    \begin{bmatrix}
    \cos\theta & \sin\theta\,\sin\phi & \sin\theta\,\cos\phi \\
    0 & \cos\phi & -\sin\phi \\
    -\sin\theta & \cos\theta\,\sin\phi & \cos\theta\,\cos\phi
    \end{bmatrix}
\end{equation}
%----------------------------------------------------

This transform is then applied to each point in each frame in the pointCloud object to move the data from the Avia frame to the World frame, as shown in Equation \ref{eqn:tform}. It is important to note that this process may introduce errors into the transformed data due to inaccuracies in the angle estimates produced by the Kalman filters.

%----------------------------------------------------
\begin{equation} \label{eqn:tform}
    \begin{bmatrix}
    x_{W} \\
    y_{W} \\
    z_{W}
    \end{bmatrix}   \;=\; R_W^A \cdot 
    \begin{bmatrix}
    x_{A} \\
    y_{A} \\
    z_{A}
    \end{bmatrix}
\end{equation}
%----------------------------------------------------

Angle estimate residuals (the difference between the motion capture ground truth and the filter's estimates) were computed for the two motion capture test cases and used as the primary metric for comparing the filters relative performance. The residuals were also used in the tuning of both filters. To tune each filter's parameters, iterative adjustments were made to the parameters, and the angle estimates observed until the mean residuals reached a minimum, as recommended by \textcite{grewalApplicationsKalmanFiltering2010}.

\subsection{De-noising}
\label{sec:ch6.section3.subsec2}

The return intensity of points can be used to remove or ignore unwanted points. A simple threshold filtering function can be constructed for de-noising data collected under snowy or other adverse conditions. To prevent valid points in the target scene with low return intensities from being discarded, a distance parameter was included in the threshold function that sets a minimum distance from the point cloud origin (the sensor aperture) that points are retained regardless of their intensity value.

%----------------------------------------------------
\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{figs/ch6/threshold_pipe.png}
    \caption{\textbf{De-noising Pipeline.}}
    \label{fig:threshold_pipe}
\end{figure}
%----------------------------------------------------

The return intensity threshold was set to 1 out of 255 and the distance threshold to 15 m. The intensity threshold was selected to be the lowest possible value to retain the maximum number of valid points, while still removing points with minimal return intensity. The distance threshold was selected based on the location of the Avia during data collection, which was always greater than 15 m above the waterline of the vessel when in calm conditions.

\subsection{Wave Parameter Estimation}
\label{subsec:ch6.section3.subsec3}

%----------------------------------------------------
\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figs/ch6/wave_est.png}
    \caption{\textbf{Wave Parameter Estimation Pipeline.}}
    \label{fig:wave_est}
\end{figure}
%----------------------------------------------------

The Aalto University wave and ice tank probe data can be used as ground truth for wave parameter estimates. Wave models were fitted to the two datasets (wave probe and Avia) and magnitude and period estimates derived from the Avia data were compared to those from the wave probe. As there was no time synchronisation between the Avia and wave probe, instantaneous wave parameters could not be compared. Instead, overall wave parameters (amplitude and frequency) for the duration of the tests were modelled and compared. The wave probe data consists of a list of wave height measurements over time, which can be modelled as a simple sinusoidal function. The point cloud data from the Avia is a spatial representation of the wave surface at a given time, which will require a more complex spatial sinusoidal plane model to be fitted to it.

The strict constraints on the wave behaviours allows for the wave models used to be greatly simplified. It can be assumed the waves will propagate uniformly across the tank with minimal change in direction and velocity.

Using the MATLAB \emph{curveFitter} tool, a sinusoidal model (equation \ref{eqn:probe_sin}) of wave height over time was fitted to the Aalto wave probe data from each test, and a single amplitude (\textit{A}) and period (\textit{t}) value was extracted per test.

%----------------------------------------------------
\begin{equation} \label{eqn:probe_sin}
    y = Asin(\omega t + c)
\end{equation}
%----------------------------------------------------

\textit{y} is the wave height at time \textit{t}, \textit{A} is  amplitude, \textit{$\omega$} is the  angular frequency and \textit{c} is the phase shift. For this investigation, only amplitude and angular frequency (\textit{A} and \textit{$\omega$}) are of interest. Phase shift is not of interest as it merely represents the starting point of the wave and does not affect the overall wave behaviour.

To model the waves from point cloud data, a spatial sinusoidal plane model (equation \ref{eqn:avia_sin}) was fitted to each frame in the point cloud using \ac{RANSAC}. Each frame fit was run for 300 iterations at an inlier tolerance of 0.02 m (2 cm). The iteration count was selected based on compute time constraints (compute time for one frame at 300 iterations was approximately 1 minute and 30 seconds, a test consisting of 3000 frames would take over 20 minutes), while the inlier tolerance was selected based on a combination of the expected wave amplitudes and the sensor's range accuracy. A function was created that accepted a point cloud frame, the number of iterations and the inlier tolerance as inputs. Six random points from the point cloud frame were selected and the sinusoidal plane model (Equation \ref{eqn:avia_sin}) was fitted to these points, using the MATLAB \emph{lsqcurvefit} function. The distance from each point in the point cloud frame to the model was calculated, and compared to the inlier tolerance to determine if the point was an inlier or outlier. The number of inliers was counted and stored, and this process was repeated for the set number of iterations. If a model fit produced more inliers than the previous best fit, then it was stored as the new best fit for that frame. After all iterations were completed, the best fit model parameters (A through F) for that frame were returned and stored in an array along with the indexes of the inliers for that fit and total number of inliers. This process was repeated for every frame in the test dataset, producing an array containing the best fit model parameters (A through F) for each frame, which were then used to calculate wave amplitude and period estimates for each frame.

%----------------------------------------------------
\begin{equation} \label{eqn:avia_sin}
    z = Asin(Bx + C) + Dx + Ey + F
\end{equation}
%----------------------------------------------------

\textit{x}, \textit{y} and \textit{z} are coordinates of the wave relative to the Avia's origin. \textit{A} is the amplitude, \textit{B} is the wave number, \textit{C} is the phase shift and \textit{D} and \textit{E} are plane slopes and \textit{F} is an offset. For this investigation only amplitude and wave number (\textit{A} and \textit{B}) are of interest.

As the waves generated in the wave tank were waves in deep water, (water depth greater than half the wavelength), wave number (\textit{k}) is related to angular velocity (\textit{$\omega$}) through the dispersion relation (\cite{dingemansWaterWavePropagation1997}) given in equation \ref{eqn:dispersion}.

%----------------------------------------------------
\begin{equation} \label{eqn:dispersion}
    \omega = \sqrt{gk}
\end{equation}
%----------------------------------------------------

Wave angular velocity (\textit{$\omega$}) can be converted to period (\textit{T}) by the relation given in equation \ref{eqn:period}.

%----------------------------------------------------
\begin{equation} \label{eqn:period}
    T = \frac{2\pi}{\omega} 
\end{equation}
%----------------------------------------------------

Once all wave number estimations were converted to wave period, the mean period and amplitude for each test, as determined by the Avia data were computed for comparison against the wave probe ground truth data.

\subsection{Pancake Identification}
\label{subsec:ch6.section3.subsec4}

To identify the shape and size of individual pancakes in the point cloud data, three density-based clustering algorithms were investigated; \ac{DBScan}, \ac{VDBScan} and \ac{OPTICS}. 

Each of these algorithms accept a point cloud frame as input and return a list, where each entry in the list corresponds to a point in the input point cloud frame. Each entry contains a cluster identification number, indicating which cluster the point belongs to. Points that are classified as noise or outliers are given a cluster ID of -1. This list can then be used to visualise the clusters by assigning each cluster a unique colour, or to calculate the size and shape of individual pancakes by grouping points with the same cluster ID. 

As no ground truth data was available for pancake size and shape, the performance of each clustering algorithm was evaluated qualitatively by visual inspection of the clustering results and comparing the number of points assigned to each cluster.

To tune the parameters of each algorithm, multiple clustering runs were performed on the same point cloud frame with different parameter combinations. The results of each run were visually inspected and compared to determine which parameter combination produced the best clustering result (most coherent pancake shapes with least over- or under-inclusion of points).

%----------------------------------------------------
\subsubsection{DBScan}
\label{subsec:ch6.section3.subsec4.subsubsec1}

The \ac{DBScan} algorithm was implemented using MATLAB's built-in \emph{dbscan} function, and is an unmodified version of the original algorithm.

%----------------------------------------------------
\subsubsection{VDBScan}
\label{subsec:ch6.section3.subsec4.subsubsec2}

The \ac{VDBScan} algorithm implemented was adapted from MATLAB's \emph{dbscan} function, with modifications to introduce variable density behaviour as described by \textcite{liuVDBSCANVariedDensity2007}. In the original \ac{VDBScan} formulation, each point is assigned its own \textbf{$\epsilon$} value derived from the local density estimated from its neighbourhood variance. Implementing this directly requires computing and storing a unique \textbf{$\epsilon$} for every point, which becomes computationally expensive and memory intensive for large point sets. To avoid this, the implementation used in this investigation replaces the per-point \textbf{$\epsilon$} values with a small set of global potential \textbf{$\epsilon$} values estimated from the distribution of the \textbf{k}-nearest neighbour distances across the full point cloud. These values act as representative density scales, allowing the algorithm to approximate variable density clustering without computing a full \textbf{$\epsilon$} profile for every individual point.

Traditional \ac{DBScan} clustering is then applied iteratively for each potential \textbf{$\epsilon$} value, producing a series of cluster label assignments over the same point cloud. To obtain a single final clustering, the labels from all runs are merged using a point-wise consensus approach, where each point is assigned the cluster ID it most frequently received across the \textbf{$\epsilon$} set. This merging allows for the most frequently detected clusters across multiple density scales to be retained, while reducing sensitivity to any single \textbf{$\epsilon$} choice.

The decision to use a modified \ac{VDBScan} implementation was made due to computational restraints. The original \ac{VDBScan} algorithm requires the calculation and storage of an individual \textbf{$\epsilon$} value for each point in the point cloud, which requires significant memory resources for large point clouds. Every attempt to run the original \ac{VDBScan} algorithm on the PC used for this investigation (equipped with 32 GB of RAM) resulted in out-of-memory errors.

\section{Summary}
\label{sec:ch6.section4}
%----------------------------------------------------

This chapter detailed the proposed data processing pipeline for data collected using the Avia sensor. The pipeline consists of three main stages: motion compensation and de-noising, wave parameter estimation and pancake identification. The motion compensation stage makes use of Kalman filters to estimate the attitude of the observation platform during data collection, and applies an inverse transform to the point cloud data to compensate for motion-induced artefacts. The de-noising stage makes use of a simple thresholding function to remove points with low return intensity, which are likely to be caused by interactions with adverse weather conditions. The wave parameter estimation stage makes use of \ac{RANSAC} to fit a sinusoidal wave model to the point cloud data, allowing for the estimation of wave amplitude and period. Finally, the pancake identification stage makes use of three density-based clustering algorithms (\ac{DBScan}, \ac{VDBScan} and \ac{OPTICS}) to identify individual pancakes in the point cloud data and estimate their size and shape.
